# 注释与文档写法

> **状态**：✅ 现行 — 本仓库注释的既有约定（不是新规定，是把已经写了几百处的习惯写下来）；`make doc-check` 会校验头文件注释覆盖率。

代码告诉读者「怎么做的」，注释要告诉读者**「为什么这么做、边界在哪、哪里会错」**。
本仓库的注释密度偏高，是有意的：这里的很多决定是「试过、炸过、改掉」的产物，
不写下来下一轮就会再炸一次。

---

## 1. 头文件：三段式

每个 `.h` 在 include guard 之后必须有一段文件头注释（118/118，由 `make doc-check` 校验）：

```cpp
// GN_Ragdoll.h — 布娃娃（C3b，纯 CPU）
//
// 解决的问题：角色"死亡"或"被击飞"时，播放一段预制动画显得假 —— 倒地位置、
// 山坡坡度、撞到什么东西都不影响结果。布娃娃让身体由物理驱动。
//
// ═══ 设计：每根骨头一个刚体（默认球体）+ distance 关节 ═══
// ...（映射方式、为什么这么选、代价）
//
// 代价：没有关节角限制（膝盖能反向弯）。这是刻意的取舍 ——
// 引擎目前没有"带角限制的球窝关节"，硬加会引入一个大得多的求解器改动。
```

三段分别回答：

| 段 | 回答的问题 | 缺了会怎样 |
|---|---|---|
| 是什么 | 这个文件负责哪一块 | 读者要在 3000 行里猜 |
| 为什么需要它 | 不做会怎样、替代方案是什么 | 下一轮重写一遍，或"优化"掉不该动的部分 |
| 边界与代价 | 什么没做、什么情况下会错 | 使用者按想象使用，然后在边界上炸 |

## 2. 契约要写在**声明处**，不是实现处

调用方只看头文件。所以「输入前提、不变量、失败语义」写在声明上一行：

```cpp
// 按注册顺序给"开了 cube shadow 的点光/聚光"分配层号。
// maxLayers 超过 GN_MAX_CUBE_SHADOW_PICKS 时会被钳制（cube array 只有那么多层）。
sCUBE_SHADOW_LAYOUT assignCubeShadowLayers(const sLIGHT_UBO &light,
                                          uint32_t maxLayers = GN_MAX_CUBE_SHADOW_PICKS);
```

参数单位的陷阱必须显式写出来 —— 本仓库真实踩过：

```cpp
float aFovY;                     // **度**
float aFovYRad;                  // **弧度**
```

## 3. 数字必须有出处

不写「更快」「明显改善」，直接写测出来的数和怎么测的：

```cpp
// 实测 0.06 时最短那根骨（0.126 m，球半径 0.063）会穿过地面掉下去（穿地 100 m，
// 动能涨到 750）…… 0.09（略大于单帧位移）就能稳住。默认值取 0.09。
```

没测过的不要写成结论。区分三种口径，并且只用这三种：

- **实测**：给了命令/场景/数字；
- **静态确认**：读了代码/规格确认，但没跑；
- **未验证**：明确写出，不要含糊。

## 4. 不要用 TODO 悬挂未做项

代码里只有一个 `TODO`（glTF alphaMode 的 BLEND 路径）。约定是：

- **未做** → 记进 [`REMAINING_GAPS.md`](REMAINING_GAPS.md)，代码里只写边界（「BLEND 未实现，按 MASK 存」）；
- **已知 bug 但本轮不修** → 记进 [`DEFECT_ANALYSIS.md`](DEFECT_ANALYSIS.md)，带锚点；
- **不能改的历史契约** → 写成契约注释（「调用方必须提供足够空间」），不要留 `TODO: verify`。

理由：`TODO` 没有负责人、没有验收、不会进 `make ci`，只会越积越多
（本仓库曾经有 36 处 `TODO: verify buffer size`，最后逐个核销为 0）。

## 5. 注释与代码必须同源

改了实现必须同步改注释，否则注释变成负资产。反面例子（真实发生过）：

- 布娃娃默认从胶囊改成了球体，文件头还写着「每根骨头一个胶囊」；
- 多层渲染的 CPU 侧已经落地，文档开头还写着「设计规划（未实现）」。

这类不一致比缺注释更糟：读者会相信注释，然后调到怀疑自己。

**批量改注释时的行尾陷阱**：`src/core/`、`src/ui/`、`src/audio/` 下的老文件是 **CRLF**，
用「读文本 → 改 → 写文本」的方式批量插入注释会把整文件转成 LF，产生上千行假 diff。
批量改写请用二进制模式并保留原行尾（或用 `unix2dos` 转回）。

## 6. 不要复读代码

```cpp
x++;                    // ❌ 把 x 加一
x++;                    // ✅ 不需要注释
```

值得写的情况只有三种：**非显然的常量**（0.09 不是随便取的）、
**反直觉的顺序**（必须先 A 再 B，否则 C 失效）、**看起来可以简化但不能简化**的地方（写清为什么）。

## 7. 演示与测试也是文档

`tests/unit/test*.cpp` 的用例名与注释是**最准的用法说明**：
每个模块都有正例和反例，「反例为什么反」比函数签名信息量大得多。
演示程序里的姿态/方向问题（腿反了、脚左右摆）都靠 `tests/common/demoPoseCheck.h` 自查，
不要靠眼睛。
